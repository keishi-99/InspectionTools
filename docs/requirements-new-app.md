# 新アプリ 要件定義書

製品ごとの検査項目に沿って複数台を検査し、結果を画面で確認しながら、検査終了後に製品別の Excel テンプレートへ転記するアプリの要件。

## 1. 構成方針

- 新アプリは、既存アプリ（InspectionTools）とは別のアプリとして作成する。
- リポジトリは分けず、同じソリューションにプロジェクトを追加する。
- 既存アプリの `Common/` にある測定器制御（Devicecontroller、InstrumentService、USBDeviceManager、InstClass 系など）を共通ライブラリへ切り出し、新旧アプリで共有する。
  - 画面に関わるファイル（HelpWindow、ScreenCaptureWindow、WaitingCircle など）は切り出し対象外。
  - 既存アプリの `Product/` は変更しない。
  - 切り出し後も、既存アプリが従来どおり動作すること。
- ホットキー機能（Win32ApiManager）と、別ソフトの画面操作に使う Win32 関連の処理も、共通ライブラリから再利用できるようにする。
- 分担は次のとおり。
  - コードで書くもの: 測定の手順、計算、別ソフトの画面操作
  - JSON で設定するもの: 合格範囲、Excel のセル位置、テンプレート名

```
InspectionTools.sln
  Instruments (共通ライブラリ)   測定器制御、Win32 関連
  InspectionTools (既存アプリ)    参照の付け替えのみ
  新アプリ
    検査の共通部分               結果クラス、進行制御、途中保存
    Excel 転記                   ClosedXML
    製品ごとの定義               検査項目、手順(コード)、設定(JSON)
```

## 2. 検査項目

### 2.1 項目の種類

| 種類 | 値の決まり方 | 判定 |
|---|---|---|
| 測定項目 | 測定器または別ソフトの画面から取得し、入力欄に表示する | 合格範囲と比較して自動判定 |
| 入力項目 | 製品の表示を見て、入力欄に数値を入力する | 合格範囲と比較して自動判定 |
| 確認項目 | 値なし。測定器を操作して波形などを見る | 人が合格/不合格ボタンで決める |
| 作業項目 | 値なし。測定器の操作や製品側の作業だけを行う（例: DCS を 4mA にして製品を調整する）。Excel に記録しない | 判定なし。作業が終わったら完了の操作をする |

- 作業項目は、DataGrid に行として出す（値の列は空欄にして、完了したかどうかだけを表示する）。Excel には書き込まない。
- 測定項目・入力項目・確認項目は、Excel の1行に対応する。作業項目は、Excel の行に対応しない。
- どの種類でも、測定器を複数回操作する手順を持てる。手順は「次の手順」ボタン（またはキー）で1つずつ実行する。
- 1項目につき結果は1つ。手順ごとの判定は行わない（例: 設定1と設定2で波形を確認し、すべての手順を見終えたあとで人が合否を判定する）。
- 値は数値のみ。
- 合格範囲（下限・上限）は、製品・項目ごとに JSON で設定する。

### 2.2 測定器の設定

- 各項目は、測定器に取らせる状態を、役割ごとに宣言する（設定名 = 値）。項目が書かなかった役割は、出力する機器（DCS、FG）なら自動で OFF に戻し、測定する機器（DMM、CNT）なら触らない（11.6 参照）。
- 実行時は、アプリが最後に適用した状態を記憶し、目的の状態との差分だけを測定器に送る。
  - 同じ項目の再測定では、差分が空になり、何も送らない。
  - 任意の項目へ移動しても、必要な差分だけが適用される。
- 測定器への接続時に初期値にしてから、項目1の設定を適用する。
- 設定の適用順序の制約（電源系の出力 ON/OFF と電圧設定の順序など）は、測定器ごとのドライバ側で保証する。順序の制約は、最初の製品の実装時に既存コードから確認する。
- 対象の測定器: 電源、マルチメーター、電圧電流発生器、周波数発生器、オシロスコープ、ユニバーサルカウンタ。
- 測定器を手動で操作した場合に備え、「全設定を再適用」ボタンを用意する。

## 3. 画面

### 3.1 DataGrid

- 列が台数、行が検査項目。1項目 = 1行、1台 = 1列。
- 判定は、セルの背景色で示す（NG は赤など）。
- セルは直接編集できる（数値のみ）。編集後は合格範囲で自動再判定する。
- 任意のセルを選んで、その項目・台へ移動できる。

### 3.2 操作 UI

- 入力欄: 取得した値、または手入力した値を表示する。
- ボタン: 取得、次の手順、合格、不合格、確定、前後の項目への移動、全設定を再適用、検査終了。
- 入力欄の値は、「確定」ボタンを押したときにセルへ反映する。
- DataGrid のセル編集と入力欄は、どちらも同じ「値の設定」処理を通す。
- 再測定は、既存セルの上書きとする。

### 3.3 台数と進め方

- 台数は検査開始時に入力する。途中で変更できる。
- 値の入った台を減らすときは、確認ダイアログを出す。
- 台数は「＋」「－」のボタンでも、入力欄への直接入力（Enter またはフォーカスを外したとき）でも変更できる。直接入力で複数の台がまとめて削除されるときも、確認は1回で、削除される台の範囲を示す。数字でない入力は元の台数に戻す。
- 台数の上限は製品の定義（`maxUnitCount`）で決める（EL5000AC は 30）。上限を超えた入力はメッセージを出して元に戻す。
- 進め方は台ごと（1台目の全項目を終えてから2台目へ）。

### 3.4 製品の選択

- 既存アプリと同じ、メニュー画面から選ぶ形式。

## 4. キー操作とフォーカス

- 新アプリと別ソフトのウィンドウは、重ならない配置で運用する。
- グローバルホットキーは1つだけ。「新アプリを前面に出してフォーカスする」。
- そのほかの操作（取得、次の手順、次/前の項目、合格/不合格、確定など）は、新アプリにフォーカスがあるときだけ効くローカルのキー割り当てとする。
- キー割り当ては、設定で変更できる。既存アプリから配置を変更する予定で、具体的な配置は後で決める。
- 別ソフトを自動操作したあとのフォーカスは、既定で新アプリへ戻す。別ソフトで人が入力する手順だけ、手順ごとに「別ソフトに残す」と指定する。

## 5. 別ソフトの操作

- 製品側の操作（設定ソフトの画面操作、値の取得）は、既存アプリと同じウィンドウ操作の方式で、製品ごとのコードとして移植する。
- 値の取得元は、測定器、別ソフトの画面、手入力の3種類。いずれも入力欄に値を表示する流れは同じ。
- 新アプリが取得した測定値を、別ソフトの入力欄へ送る手順を定義できる。
- 別ソフトへ値を送る前に、送り先のウィンドウ（タイトルなど）を確認する。違う場合は、送らずにメッセージを出す。

## 6. 結果の保持と Excel 転記

### 6.1 保持

- 検査中はメモリ上で保持し、値を設定するたびに JSON へ途中保存する。
- 保存先は製品ごとに1つのファイルとし、同じファイルに上書きする。書き込み中にアプリが落ちても古い完全なファイルが残るように、別名の一時ファイルに最後まで書いてから置き換える。
- 保存するのは検査中の状態だけ（台数、現在位置、実施済みのセル）。項目の定義は保存しない（製品ごとの JSON から毎回読み込めるため）。
- 起動時に途中保存が残っていれば、「続きから再開しますか」と確認する。
- 復元できないとき: 保存内容が壊れている、または項目の定義と合わない（製品、項目数、台数、位置が合わない）ときは、「復元できません」と知らせて、新しく始める。元のファイルは、`{製品名}.broken-{日時}.json` という別名で残す。
- 転記が成功したら、その製品の途中保存を削除する（次の起動で「続きから再開しますか」と聞かれないようにするため）。転記に失敗したときは、途中保存を残し、原因（Excel で開いている、別の製品のテンプレートを選んだ、など）を直してから、復元してやり直せるようにする。退避した壊れたファイルは削除しない。
- 値の項目（測定項目、入力項目）は、復元時にいまの合格範囲で判定し直す（保存後に項目の定義が変わっていても、判定を合わせるため）。
- 保存した結果を後から検索する機能は不要。
- 手動で入力・編集した値は、内部の JSON に「手動」と記録する。Excel には出さない。

### 6.2 転記

- 検査終了ボタンで合否を判定し、製品別のテンプレートへ転記する。
- NG が残っている場合は、確認ダイアログを出してから転記する。
- 転記先は、あらかじめ別名で保存済みのテンプレートのファイルとする。検査終了時にファイル選択ダイアログで選び、アプリはそのファイルを開いて値を書き込み、同じ名前のまま上書き保存する（ファイル名の変更や命名規則は不要）。
- 書き込む前に、選んだファイルが正しい製品のものかを確認する。製品ごとの JSON に、確認用のセルと期待する値を持たせ、読み取った値が違う場合は、書き込まずにメッセージを出して中止する。
- 確認用のセルに加えて、書き込み先のシートが存在することも確認する（同じブックに AC 用と DC 用のシートがあるため）。
- 合否の判定式はテンプレート側に入っているため、アプリは測定値と確認結果の値だけを書き込み、判定の列には触れない。
- 確認項目は、OK のときテンプレートの規定の文字（例: 「良」）を書き込み、NG のときは空欄にする。
- シリアル番号は、新アプリの転記が終わったあとに、操作者がテンプレートのファイルへ直接手入力する。新アプリはシリアルを扱わず、書き込まない（台ごとのシリアルはテンプレートの数式で自動的に並ぶ）。
- 合格範囲は製品ごとの JSON に持つ。転記の直前に、テンプレート内の合格範囲のシートと JSON の範囲を突き合わせ、違う場合は警告する。
- シート名は完全に一致させる（テンプレートには末尾に空白を含むシート名がある）。
- 転記先に値がすでに入っていても、確認なしで上書きする。
- 転記先のファイルが Excel などで開かれていて保存できない場合は、「閉じてから再実行してください」とメッセージを出す。結果は途中保存の JSON に残し、再実行できるようにする。
- ClosedXML を使い、Excel の起動やキー入力の自動送信は行わない。
- 保存は、別名の一時ファイルに最後まで書いてから置き換える（書き込み中に失敗しても、元のファイルが壊れないため）。保存のとき、Excel で開いたときに1回だけ全部の数式を計算し直す設定（`fullCalcOnLoad`）にする（書き込んだ値に合わせて、判定の欄を更新するため）。
- 検査した台のセルだけを書き換える。測定項目・入力項目は、値があれば数値で書き（合格範囲の外でも書く。判定はテンプレートの数式が行う）、未実施なら空欄にする。確認項目は、合格のときだけ規定の文字を書き、不合格と未実施は空欄にする。作業項目は書かない。検査していない台の列には触れない。
- ClosedXML は、読み込んだ時点でシートの表示形式（改ページプレビュー）を保持できず、保存し直すと通常表示に戻る。回避策として、保存の直前に、すべてのシートを改ページプレビューにそろえる。現在のテンプレートはすべて改ページプレビューで運用しており、ほかの表示形式の予定はない。通常表示のシートを残す必要が出たら、製品ごとの設定で、改ページプレビューにするシートを選べるようにする。ACdata を開いたときのスクロール位置とカーソル位置も保持されない（F列から表示が始まる）が、新アプリはセルの位置を指定して書き込むため問題ない。
- 転記先は、1項目につき1セル（項目全体の結果）。位置は製品ごとの JSON で設定する。
- 配置は、台数が列、検査項目が行。製品によっては、一定台数ごとに同じ列のまま一定行下へ折り返す。

```
列 = 開始列 + (台番号 % 折り返し台数)
行 = 項目の行 + (台番号 / 折り返し台数) * 行オフセット
```

製品ごとの JSON の例（`transfer` が転記の設定。`unitsPerBlock` と `blockRowOffset` は、折り返す製品だけに書き、両方そろえる）:

```json
{
  "product": "EL3801",
  "maxUnitCount": 8,
  "transfer": {
    "dataSheet": "Data",
    "settingSheet": "Setting",
    "firstRow": 5,
    "lastRow": 30,
    "verifyCell": "B2",
    "verifyValue": "EL3801",
    "firstUnitColumn": "C",
    "unitsPerBlock": 4,
    "blockRowOffset": 20
  },
  "items": [
    { "name": "出力電圧", "kind": "Measurement", "excelRow": 5, "lowerLimit": 11.5, "upperLimit": 12.5 }
  ]
}
```

### 検査終了ボタンの流れ

1. 転記先のテンプレート（Excel ブック）を、ファイル選択のダイアログで選ぶ。選ばずに閉じたときは何もしない。
2. 製品の確認（`verifyCell` の値）を行い、違えば転記せず中止する。
3. 合格範囲の突き合わせを行い、食い違いがあれば内容（先頭10件まで）を示して、転記するか確認する。
4. 未実施の測定項目・入力項目・確認項目があれば、転記先の該当セルが空欄になることを示して、転記するか確認する（作業項目は数えない）。
5. 転記する。成功したら途中保存を削除し、完了を知らせて、新しい検査（1台）にする。
6. 転記に失敗したとき（違う製品、ファイルが開かれている、読み取れない）は、理由を知らせる。結果は途中保存に残るので、原因を直してもう一度押せばやり直せる。
7. 転記は成功したが途中保存の削除に失敗したときは、転記は済んでいることを知らせ、次回の起動で「続きから再開しますか？」と出たら「いいえ」を選ぶよう案内する。新しい検査にはする。

## 7. テスト方針

測定器との通信をダミーに差し替えられるようにして、ロジックの大半を自動テストで確認できるようにする。

- 通信の継ぎ目として、`DeviceController.ConnectAsync` と同じ形の interface（`IInstrumentConnection`）を共通ライブラリに用意する。新アプリの各クラスは、これをコンストラクタで受け取る。
  - 本物は、既存の `DeviceController` に処理を渡すだけのアダプタとする。既存の `DeviceController` と旧アプリのコードは変更しない。
  - 測定値の読み取り（`InstrumentService`）には、`IInstrumentConnection` を引数に取る版を追加する。既存の版は、本物を渡してその版を呼ぶ形にして、呼び出し側を変えない。コマンドの文字列は1か所に保つ。
  - ダミーは、送られたコマンドを記録し、次の規則で返事を返す。
    - 通信方式は VISA のみを対象とする（ADC は対象外）。
    - 返事を求めない通常のコマンドは、返事を返さず、送られたコマンドだけを記録する。
    - `*OPC?` で終わる問い合わせには `"1"` を返す。
    - `Index` が -1 の測定器には `""` を返す（本物の `ConnectAsync` と同じ）。
    - 測定値の読み取り（`FETC?`、`MEAS:CURR?`、`:MEAS?XNOW`、`MEASU:MEASn:VAL?`）には、テストごとにコマンドと値の待ち行列を指定して、順に返す。待ち行列が空になったら `1.234` を返す。範囲内の値と範囲外の値、台ごとに違う値を作り分けて、判定のテストに使う。
    - 送られたコマンドは、送られた順の一覧として読み取れる。
    - 上記以外の問い合わせが来た場合は、エラーにしてテストを失敗させる（コマンドの打ち間違いや、未対応の測定器に気づくため）。
- テストプロジェクトは `InspectionTools.Instruments.Tests`（xUnit）とし、ソリューション直下に置く。ダミー（`FakeInstrumentConnection`）はテストプロジェクトの中に置く。
- COM 参照（`VisaComLib`）は `dotnet build` では処理できない可能性が高い。ビルドは Visual Studio 付属の MSBuild で行い、テストは `dotnet test --no-build` で実行する。手順2の最初に、この流れが動くことを確認する。
- 読み取りコマンドかどうかの判定は、ダミーの動きの要になる部分なので、開発者本人が実装する。
- 自動テスト（`dotnet test`）で確認するもの:
  - 項目の進行、台の切り替え、任意のセルへの移動
  - 測定器の設定の差分適用（ダミーが記録した送信コマンドの内容と順序）
  - 合否の判定、合格範囲とテンプレートの突き合わせ
  - 途中保存と復元
  - Excel への転記（出力したファイルのセルを読んで確認）
- 通信ログの取得は行わず、実機の返事のサンプルも取らない。測定値の読み取りに指定がないときの標準の返事は `1.234` とする。
- 実機が指数表記（例: `+1.234E+00`）で返す場合に備え、数値変換のテストでは指数表記の文字列も確認する。実機の返事の形式が想定と合うかは、実機での確認で見る。
- ダミーが記録した送信コマンドの列を、既存アプリのコードに書かれているコマンドと照合する。
- 測定値の文字列を数値に変換する処理は、変換に失敗しても黙って 0 を返す作りになっている。新アプリでは変換に失敗したらエラーとして扱い、テストで確認する。
- テスト用の Excel テンプレートは、実物の代わりに、同じセル配置と数式を持つ仮のテンプレートを作成してリポジトリに置く。実物のテンプレートはリポジトリに置かない。
- 自動では確認せず、人が実機で確認するもの:
  - 実機との通信とタイミング、実機が返す値の形式
  - 別ソフトの画面操作
  - グローバルホットキー
  - 画面の見た目と操作感

## 8. 進め方

1. `Common/` の測定器制御を共通ライブラリへ切り出す。
   - 検証: 既存アプリの全製品画面が従来どおり起動し、測定器につながること。
2. 測定器との通信の継ぎ目（interface）とダミーを追加し、テストプロジェクトを作る。手順1が `main` に入ってから、最新の `main` から始める。
   - 2-0. MSBuild でのビルドと `dotnet test --no-build` が動くことを、空のテストで確認する。
   - 2-1. `IInstrumentConnection` と本物のアダプタを共通ライブラリに追加する。検証: 旧アプリがビルドでき、既存の呼び出しが変わらないこと。
   - 2-2. `InstrumentService` に、`IInstrumentConnection` を引数に取る版を追加する。検証: ダミー経由で `FETC?` が送られ、`1.234` が返ること。
   - 2-3. `FakeInstrumentConnection` と、その規則のテストを追加する。検証: ダミーの規則の各行がテストで確認できること。
3. 結果クラスと途中保存（JSON）を追加し、1製品だけ対応する。
   - 検証: アプリを落としても、再起動で結果を復元できること。

## 10. 確認が必要なリスク

### 11.3 作業項目

旧アプリの DCS の順番表（22段階）のうち、Excel の行に対応するのは、後半の `4mA・12mA・20mA・1V・3V・5V` が2回続く12段階（行18〜23、行24〜29）である。先頭の `OFF → 4mA → 20mA → 5V → 1V → 4mA → 20mA → 5V → 1V` のうち、最初の `OFF` は出力の初期状態で、続く `4mA → 20mA → 5V → 1V` を2回繰り返す8段階は、Excel に記録しない作業（アナログ入力1・2の調整と推定）なので、作業項目として DataGrid に出す。調整のあとの `OFF`（出力を止める操作）は作業項目にしない（行16・17の温度入力では DCS を使わないため、そこで自動的に OFF になる）。作業項目は、行15（密度計用電源）の後、行16（温度入力）の前に置く。先頭に Pt100 の校正作業2つ（80.306Ω、229.716Ω。アプリが管理しない機器で行う）、続けてアナログ校正8つ（`アナログ校正 入力1 DCS 4mA` など）の順に並べる。

### 11.5 定義ファイルと生成ツール

- `products/EL5000AC.json`: EL5000AC の定義。記録する 46 項目（測定 17、入力 22、確認 7）と、作業項目 10 個を、検査の流れの順に並べている。


### 11.6 測定器の手順表

項目ごとの測定器の動作は、製品の定義の各項目の `actionId` で指定し、`InspectionTools.Products` の `El5000AcProcedure` の手順表を引く（`actionId` のない項目は、測定器を使わない）。

- 役割は `Dmm01`、`Dmm02`、`Fg`、`Dcs`、`Cnt`。
- 動作は、測定器に取らせる状態（役割と状態の名前）と、値の取得（役割、倍率、小数の桁数）で表す。
- **出力する機器（DCS、FG）**は、項目が指定しないとき自動で OFF に戻す。**測定する機器（DMM01、DMM02、CNT）**は、項目が指定しない限り触らない。測定値を取得する項目が、必要なモードを指定する。
- 状態は覚えておき、現在の状態から変わる役割にだけコマンドを送る。接続していない役割は無視する。
- 値の取得は、旧アプリの入力と同じ換算にする（DMM01 は mA で小数3桁。DMM02 は DCV が V で小数4桁、DCI が mA で小数4桁。CNT は ms で小数3桁。四捨五入は 0 から遠い方向へ）。測定値の返事が数値に変換できないときは、0 にせずエラーにする。CNT は、値を読み取るたびに `:FRUN ON` を送る。

| 動作 ID | 使う項目 | 測定器の状態 | 値の取得 |
|---|---|---|---|
| `dmm01-aci` | 行8 | Dmm01=ACI | Dmm01 ×1000 |
| `dmm02-dcv` | 行9〜15、33〜35 | Dmm02=DCV | Dmm02 ×1 |
| `dmm02-dci` | 行30〜32 | Dmm02=DCI | Dmm02 ×1000 |
| `cnt-pulse-width` | 行36〜38 | – | Cnt ×1000 |
| `dcs-4mA`、`dcs-20mA`、`dcs-5V`、`dcs-1V` | アナログ校正の作業8項目 | Dcs=その値 | – |
| `dcs-4mA`、`dcs-12mA`、`dcs-20mA`、`dcs-1V`、`dcs-3V`、`dcs-5V` | 行18〜29 | Dcs=その値 | – |
| `fg-on` | 行47 | Fg=ON | – |

コマンドは旧アプリのものと同一にし、テストで旧アプリのソースにある文字列と照合する。
